## ① 危险方向错误：它为什么最危险，怎么锁住

### 问题

校准集 `data/calibration/event_judgments.json` 是 **n=10 的人工复核留出集**
（`_holdout_rule` 保证它**不进 RAG 索引**）。在 v3 上实测：

| 用例 | 期望 | v3 实判 | 性质 |
|---|---|---|---|
| `peer-amd-rumor` | `caution` | `none` | 🔴 **危险方向**：该停手的时候说"没事" |
| `other-earnings-nb` | `none` | `block` | 过保守：该做的时候说"停手" |

两类错误的性质完全不同：
**过保守只是少赚，危险方向是"判据说没事"** —— 后者是本项目最不能接受的一类失败
（和 `analyst_execution_progress` 里那个"时钟不一致却钳成 0"是同一类错误）。

v3 的根因写在 prompt 里：它的判据明确写着"**不看它对某个标的相不相关**"，
而且没有"同业／竞争格局／产业链"这一类。所以 AMD 的传闻对 NVDA 的相关性被丢掉了。

### 修法（`prompts/event_gate.v4.md`）

改**两步判断**，顺序不能颠倒：

1. **相关性**：这条消息与我方标的相关吗（本公司 / 同业竞争 / 产业链 / 宏观 / 行业监管）？
2. **类别**：相关之后才判类别（`block` / `caution` / `none`）。

并把"同业竞争格局、产业链传导"明确归到 `caution`；同时明确
**"别家公司自己的公司行为"（如别家发布财报）不等于我方事件** —— 这一条是防止
修过头变成"什么都是 caution"。

⚠️ few-shot 例子**必须是与校准集不同的合成例子**。校准集是留出集，
把它的用例写进 prompt 等于拿测试集训练 —— 那样 10/10 就毫无意义。

### 结果与**回归锁**

```
v3-2026-09-19   一致率 80%   危险方向 1     ← 修之前
v4-2026-09-20   一致率 100%  危险方向 0     ← 门槛基线
```

基线落在 `data/calibration/baseline.json`：`min_agreement=0.9`、
`max_dangerous_errors=0`，并保留 `history`（谁在什么时候、为什么改）。

已接成 `run_p2.py --selftest --net` 的**第 ㉑ 步**：

```bash
python tools/event_calibration.py --gate
```

- 危险方向 > 0 -> **失败**；一致率 < 90% -> **失败**；比基线退化 -> **失败**。
- **没有 LLM key 时如实报"未执行"并返回 0**：既不冒充通过，也不算失败。

⚠️ 这 **n=10 是回归证据，不是准确率结论**。样本量太小，不能拿它说"判定准确率 100%"。
它的作用只有一个：**防止把已经修掉的危险方向错误改回去**。

## ② 执行进度官：把链路从"下单前"补成"执行中闭环"

### 为什么这是 P0

v1 的链路只在**开仓前**跑一次。于是**挂单一直不成交、或者只成交了一条腿的时候，
链路里没有任何角色负责** —— 而这正是赛道三「执行辅助」手册点名的位置：
trader 决策后的**拆单与滑点管理**。没有这一段，"执行辅助"就只是"决策辅助"。

### 它只回答两个问题（都可证伪）

| 判据 | 触发条件 | 级别 | 依据 |
|---|---|---|---|
| `partial_fill_naked` | 一腿已成交、另一腿超过宽限 `NAKED_GRACE_MIN=1` 分钟仍未成交 | **veto** | 实测联合分布：`P(只成交一腿)=23.6%` vs `P(两腿都成交)=3.60%` -> **6.6 倍** |
| `progress_stalled` | 挂单存活 ≥ `STALE_TRADE_MIN=30` 分钟，且**该腿**在挂单期间零成交 | caution | 挂单的收益完全来自成交；没有成交时挂单不可能成交 |

"一腿不跟是常态"这句话是**量出来的**，不是修辞：`joint_fill_all_in_house.csv`
（3671 个窗口，2026-09-12~09-14）。⚠️ 这个比值随窗口与路线变化（`joint_fill_all.csv`
上同一份代码是 **14.9 倍**），所以**代码里不写死**：报告 evidence 与自检都直接读实测表并
打印当期值。自检断言的是**关系**（比值 ≥5），不是某个具体数字。

### 红线怎么落地

1. **agent 不产出数字**：本路只给"该复核什么"的触发条件；新价位、新规模一律由确定性
   交易员给。自检直接断言假设字典里**没有** `size_usd/price/qty_usd/limit_price/target`
   这些键。
2. **数字只能来自成本模型**：`execution_actions()` 给出的补腿成本等于
   `execution_cost.analyse_two_leg` 的双腿全吃单往返成本（自检断言相等）。
   刻意**不给损益估计** —— 本项目不下单、没有持有期损益口径，
   "不处置会亏多少"这种数字**算不出来也不编**。
3. **只收紧不放松**：假设并进 `risk_officer` 的 `agent:` 规则，veto 级 -> 一票否决。

### 本轮抓到的真 bug：时钟不一致导致"判据说没事"

第一次给接线写自检时就翻车了，而**翻车本身是这次最有价值的产出**：

```
持仓单 opened_ms 用的是墙钟（now - 10min）
run_decision 里的 now_ms 是 time_basis()（读冻结快照时按**数据自带时刻**）
-> now - opened < 0
-> 初版写成 elapsed = max(0, raw_min) -> 存活 0 分钟
-> 落在宽限期内 -> 裸露敞口假设**静默消失**
-> 决策里一条 agent 规则都不产生，而页面上还显示"执行进度：正常"
```

这是最危险的一类失败（判据说"没事"）。修法：**显式拒绝判断**，不钳成 0。

```python
if raw_min < 0:
    return report(..., "neutral", 0.0, [...],
                  "持仓单 opened_ms 晚于本次决策基准时间（差 %.1f 分钟）——"
                  "两者不是同一个时钟，**不硬判**"), [], [两条留痕]
```

自检里加了对应的回归：订单时间晚于决策基准时间 -> **零假设且如实留痕**，
报告里必须写清"不硬判"。

### 契约：`order_state` 也进了复跑参数

执行进度官让"在途订单"变成了**决策的真实输入**（能改立场、能改规则表、能改否决清单）。
不记进契约，`--replay` 就会漏掉那条 `agent:` 规则，报"不一致"而真正原因是输入没被记下来。

- `PARAM_FIELDS` 增加 `order_state`（现共 12 项）。
- 存的是 `norm_order_state()` **规范化后的最小字段集**：只留 `base / qty_usd /
  spot_filled / perp_filled / opened_ms / id / synthetic`。
  持仓单里的点位、备注、券商单号这些**不影响决策**的字段一律不存 ——
  存了它们一变就误报复跑不一致。
- `--replay` 与 `tools/run_record.py` 的复跑都把 `order_state` 读回来当冻结输入。
- 自检正反两面：带订单复跑**必须一致**；复跑时**丢掉**订单**必须报不一致**。

### 接口与页面

- `/api/decision` 新增 `?position=auto|demo|none`（默认 `auto`）：
  - `auto` 读 `data/positions/open.json`（**用户/上层提供，本服务只读不写**）；
  - `demo` 造一张**现货已成交/永续未成交**的合成单，带 `synthetic: true`；
  - `none` 显式关掉。
- 演示单为什么必须有：手上通常没有真实在途订单，没有它这个功能在演示里**永远不出现**，
  等于不可验证。合成单把"看得见"和"不撒谎"同时做到：`synthetic` 标记一路进
  evidence、备注、日志、接口与页面。
- 前端新增 **⑥ 执行进度官** 面板。三条硬规矩在页面上都看得见：
  1. **没有在途订单 -> 明确说"无在途订单"，不画绿灯**（没有数据 ≠ 没有风险）；
  2. 合成单**显眼标注**，避免截图被当成真实下单记录；
  3. 未过阈值的判据**留痕不删**，让读者能判断"判据到底有没有在工作"。

## ③ 长跑记录：没有代码指纹的成功率是**不能归因**的

`tools/run_record.py` 持续记录每轮的真实决策（耗时、立场、闸门来源、LLM 是否复用缓存、
风控否决、单调性、复跑契约、保活重启、RSS）。这一轮补了一个**必须有的字段**：

```
src_sha16    关键源文件（run_p2.py + project2/*.py + tools/*.py）的 SHA-256 前 16 位
git          当时的最后一次提交
git_dirty    工作区是否领先于那次提交（实测就是：源码改了还没提交）
```

理由是实测出来的：加上指纹之前，记录里已经积了 **412 轮**，而这 412 轮**横跨了
执行进度官接入前后的两版代码** —— 把它们混在一起报"成功率 100%"是**无法归因**的。
**权威标识是 `src_sha16`**（它哈希的是工作区里的真实文件）；`git` + `git_dirty`
只是给人看的位置线索。

现在 `--report` 会按指纹分组并明确标注：

```
· (无指纹·旧记录)  413 轮 ｜ 成功 100.0% ｜ 2026-09-19T19:26 -> 2026-09-20T10:40
· 36aa881ba9f33c5b（git f82fe80＋未提交改动）  4 轮 ｜ 成功 100.0%
· 776cba88c6107b48（git f82fe80＋未提交改动）  N 轮 ｜ 成功 100.0%
```

多于一个版本时会直接写"下面的总成功率是**混合**口径，不能归因到单一版本"。

### 落盘报告：让材料里的数字能被点回去

原始记录 `data/run/record.jsonl` 是**运行时产物**（持续追加），被 `.gitignore` 排除；
但材料里引用的复用率/耗时必须能**点回仓库内一个文件**，所以：

```powershell
python tools\run_record.py --report --md --out data/derived/run_record_report.md
```

这个落盘报告**随仓库走**，且文件头自己写明"这是汇总，原始逐轮证据在本地记录里" ——
不冒充原始数据。

### 当前长跑实测（快照，**持续增长**）

```
轮数        540（成功 540 / 失败 0）
决策耗时    p50 2674 ms ｜ p95 3124 ms ｜ 最慢 8435 ms
LLM         调用 124 次 ｜ 复用缓存 120 次（49.2%）
契约复跑    181 次，通过 181 次
单调性违背  0 次
保活重启    0 次
内存        22.0 MB -> 34.7 MB
```

⚠️ 其中 **413 轮是旧代码跑的**（无指纹）。它们只能支持"长时间连续运行不崩、
复跑契约稳定、事件驱动缓存生效"这类结论，**不能**给当前代码背书。

### 🔴 指纹本身也被打脸过一次：进程级缓存 = 自信地标错

指纹刚加上时是**进程级缓存**（一次进程只算一次）。后果：记录器连续跑了几小时、
中途代码改了 3 次，它给后面 **123 轮**全都盖了**启动那一刻**的指纹。

这比"没有指纹"**更糟**：不是"没标注"，而是**标错了还让人相信**。
读者会以为这些轮次属于它标出的那一版，实际上不是。

修法：按 `_src_signature()`（每个源文件的 大小 + mtime）判断，**签名变了就重算**；
没变才复用上次的哈希（stat 很便宜，不必每轮读 20+ 个文件）。
自检用**打桩签名**验证"缓存按签名失效"，而不是按进程启动时间。

> ⚠️ **因此**：`776cba88…` 那一组里的后 123 轮，其 `src_sha16` 是
> **进程启动时刻**的代码，并不等于那些轮次实际跑的代码 —— 属于**已知的标错**，
> 不应当作依据。修复后的轮次起，指纹与轮次一一对应。
> 教训与 `tools/doc_ref_check.py` 那两处是同一个：**缓存/判定要绑定到会变的东西上**。
